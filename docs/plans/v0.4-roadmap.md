# v0.4.x roadmap

Status: v0.4.0 deployed and verified on 2026-09-20; v0.4.1 is in verification.
The owner requested Vietnamese localization, optional two-factor authentication,
a real MCP resume workflow, and better social and chat previews. Each release
below has one bounded outcome. The owner delegated review and deployment for all
rounds. Independent design review and release checks remain required. The
accepted [bilingual workspace design](../design/editor-localization.md) and
[v0.4.0 plan](v0.4.0-localization.md) govern the first release.

## Starting point

- Production serves v0.4.0. Operational acceptance remains open in the
  [production checklist](phase-10/exit-criteria.md).
- The homepage, account pages, legal pages, and template gallery support
  Vietnamese and English. The resume list, creation flow, editor, publish, and
  PDF controls also support both languages. Settings and agent consent remain
  English until v0.4.1.
- Resume language is separate from site language. Renderer labels and
  authentication email templates already support Vietnamese; authored content
  must never change when the interface language changes.
- Accounts use a password or an enabled identity provider. There is no second
  authentication factor.
- MCP provides fifteen private resume tools through user-authorized OAuth.
  Publishing remains a web action under
  [ADR 0026](../adr/0026-mcp-agent-access.md).
- Platform pages have social metadata. Published resumes have a live-gated 1200
  by 630 share image under [ADR 0032](../adr/0032-public-share-image.md).

## Localization boundaries

Reuse the existing Vietnamese and English locale system. Add matching keys and
tests for complete coverage, including validation messages, dialogs, loading
states, and assistive text. Do not localize API error codes, identifiers, or
stored user content. Preserve a user's language choice across sign-in and
navigation.

Review Vietnamese wording throughout creation, editing, publishing, export,
account, and consent flows. The owner waived a separate human review gate. Use
fictional fixtures for automated tests. Check text fit, diacritics, keyboard
use, and phone layouts in both languages. Changing the site language must leave
saved resume text and resume language unchanged.

## Two-factor authentication proposal

The owner selected both passkeys and authenticator-app codes, delivered in
separate small releases. The proposed order is passkeys requiring local user
verification in v0.4.2, then TOTP codes in v0.4.3. Both methods remain optional
and include single-use recovery codes. Each release must provide a complete
enrollment, sign-in, sensitive-action verification, removal, and recovery flow.
The authentication contract still needs design review before implementation.

The security design must cover these rules:

- Enrollment requires recent authentication and proof that the new factor works.
  Do not enable enforcement for an incomplete enrollment.
- Password and provider sign-in both honor the account's second-factor setting.
  Primary authentication alone cannot issue a fully authenticated session for an
  enrolled account. Agent consent and sensitive-action reauthentication must
  honor the same boundary.
- Challenges are short-lived, single-use, account-bound, and rate-limited.
  Passkeys require exact origin and relying-party checks plus user verification.
- Recovery codes are shown once, stored only as hashes, and consumed atomically.
  Password reset or provider relinking cannot silently remove the second factor.
- Enrollment, factor replacement, removal, and recovery require a deliberate
  flow, security notification, and a defined session and connected-agent
  revocation policy. Sessions and grants issued before enrollment must not
  bypass the newly enabled requirement.
- Each security release includes enrollment, recovery, concurrency, replay,
  bypass, and lost-factor tests, with an independent adversarial review.
  Translate every new security screen in the same release.
- Deploy with enrollment disabled until the complete flow is verified. After
  enrollment is enabled, a rollback must preserve enforcement for enrolled
  accounts; an older version that ignores factors is not a valid rollback.

Passkeys come first because WebAuthn credentials bind authentication to the
relying party. Authenticator-app codes follow in their own release and are not
phishing-resistant. See the
[WebAuthn specification](https://www.w3.org/TR/webauthn-3/) and
[OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).

## MCP acceptance and privacy

Run destructive and adversarial tests locally with synthetic accounts first. The
production check uses only the account the owner explicitly authorizes. Load
credentials at runtime from an ignored local file with owner-only permissions.
Never copy credentials, account identifiers, or real resume content into source,
fixtures, documentation, commits, screenshots, or logs.

Verify discovery, explicit OAuth consent, tool listing, read and write,
idempotent retry, stale-revision handling, and revocation of the test grant.
Operate only on the resume created for this check. If the account is at its
resume limit, stop rather than deleting an existing resume.

Use owner-supplied career facts, preserve Vietnamese diacritics, and review the
result in the editor and PDF. Keep the English source unchanged and the new
Vietnamese resume private. Publishing requires a separate owner request. MCP
gains no publishing tool. Retain only redacted pass/fail evidence and remove
temporary tokens and artifacts after the check.

## Social and chat previews

Treat platform pages and resumes as separate releases because their privacy
rules differ. Platform pages need clear product or template titles,
descriptions, canonical URLs, language metadata, and a branded preview image.
Resume previews must derive only from the current public snapshot: the sanitized
resume projection plus validated public head settings under
[ADR 0042](../adr/0042-public-page-title-and-favicon.md). Preserve an owner-set
public title in preview metadata without adding those settings to public JSON.
No account email, private field, hidden entry, or storage key belongs in a card.

Verify server-rendered Open Graph and X card metadata with absolute HTTPS image
URLs, explicit image dimensions, content type, and useful alternative text.
Check the resulting cards in Facebook, LinkedIn, Zalo, and at least one other
chat app. Use fictional published resumes, inspectors, and unsent drafts for
these checks. Do not send or publish messages as part of preview verification.

Platform crawlers receive Vietnamese by default because the site uses one
canonical URL with a language cookie. Do not promise language-specific cards
without a separate URL design. Resume metadata follows the resume language.
Update the public renderer and Go HTML validator together so the metadata
allowlist accepts only the intended escaped values.

Cover Vietnamese and English, custom and default public titles, long names and
headlines, photos and no photos, discovery disabled, PDF download disabled,
renamed URLs, unpublishing, and deletion. Preserve the existing separation
between a live shared link, discoverability, and download permission. Any change
to that contract needs a design decision before implementation.

Unpublishing must stop fresh origin reads. A platform may retain a card it
already fetched; do not promise that revocation erases third-party caches.
Document the measured behavior and supported refresh tools.

Use the [Open Graph protocol](https://ogp.me/) and
[LinkedIn's sharing requirements](https://www.linkedin.com/help/linkedin/answer/a521928/making-your-website-shareable-on-linkedin?lang=en)
as references. These define metadata requirements, not a guarantee that every
app displays the same card.

## Delivery

Review and ship one release at a time. Run the affected checks locally, require
green GitHub CI on the exact commit, then tag, deploy, and verify production.
Retain open production acceptance work until its own evidence is complete. Do
not include account data or unrelated deployment changes in these releases.
