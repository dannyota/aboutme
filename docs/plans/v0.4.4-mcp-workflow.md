# Official SDK owner workflow implementation plan

> **For implementation workers:** Use `superpowers:subagent-driven-development`
> to execute this plan through the repository role briefs and review gates.

Status: planned. The accepted design passed independent review. Implementation
starts after the top manager accepts this plan. The plan targets v0.4.4 from
base `93dc375209987f298bb17a0fd188f390c27161bb`.

**Goal:** Prove aboutme interoperability through the pinned official Go MCP SDK,
then create exactly one new private Vietnamese resume from the owner's only
English resume without changing, publishing, or deleting the source.

**Architecture:** A host Go runner owns SDK discovery, OAuth, Streamable HTTP,
tool calls, private artifacts, validation, mutation caps, and recovery. A pinned
Playwright helper owns browser login and consent through private handoff files.
The manager supplies and reviews one private translated candidate between the
read and create stages.

**Tech stack:** Go 1.27.1, `github.com/modelcontextprotocol/go-sdk v1.7.0`,
Playwright 1.62.1, the native HTTPS stack, and the existing MCP and OAuth
services.

**Spec:** [MCP owner workflow](../design/mcp-owner-workflow.md) and
[ADR 0026](../adr/0026-mcp-agent-access.md).

## Accepted design gate

The accepted design closes these implementation prerequisites:

- Dynamic client registration accepts the SDK's inferred exact
  `application_type: native` for a loopback public client. Other values,
  duplicate fields, and unsupported SDK fields remain closed. The runner sends
  only `client_name`, one loopback `redirect_uris` value,
  `token_endpoint_auth_method: none`, and the SDK-inferred application type.
- Protected-resource metadata advertises exactly `resumes:read` and
  `resumes:write`, which supplies the official SDK's requested scopes. The
  authorization-server metadata retains the same exact scopes.
- The launcher exposes only a dedicated browser-handoff directory and one exact
  staged credential file to the browser container. It never mounts the workflow
  directory, source, candidate, photo, create journal, or unrelated credentials.
  Local mode generates a run-private synthetic fixture file. Production alone
  mounts the validated owner credential file at the same container path.
- Local success writes the private versioned SDK proof attestation defined by
  the design. Production validates its 24-hour time bound and every release,
  binary, launcher, staged browser source-closure, and image binding before it
  resolves or stats the owner credential path.
- A durable ignored production-completion sentinel is checked before OAuth or
  resume reads and is atomically written before successful cleanup. It contains
  no owner data or identifiers and prevents a second production create.
- The versioned revocation journal attests the workflow, origin, confirmed
  target, and same-origin confirmation time. Under the production lock,
  revocation-only recovery creates and syncs a missing matching completion
  sentinel before any revocation action or journal deletion. Failure retains the
  journal.
- The SDK has no revocation helper. The design permits one narrow RFC 7009 POST
  of the current refresh token with `token_type_hint=refresh_token`, through the
  restricted client. It defines secret-free retry and recovery after an unknown
  response.
- When the completion sentinel exists with unresolved revocation, startup allows
  only revocation recovery. A private mode-`0600` journal retains the minimum
  exact retry authority and server-bound expiry cutoffs. A timely access-token
  `401` or refresh-token `invalid_grant` proves revocation. The recovery path
  journals rotated tokens before further calls and cannot reopen resume reads or
  mutations.

No worker may change these contracts or invent a replacement. Contract changes
return to the architect and a fresh reviewer before implementation continues.

## Implementation boundaries

The design owns the exact wire and private-file shapes. Implementers must not
copy those shapes into a second public contract. Keep the runner in one command
package with unexported types and narrow internal interfaces for the SDK tool
client, browser handoff, clock, entropy, listener, and HTTP transport.

Use distinct source and target handle types so a source identifier cannot reach
a mutation call. Go alone validates the loopback callback. The browser helper
returns only a fixed result code through the design's private handoff.

Persist the complete byte-equivalent create intent before its first send. Exact
replay ends at the design's 12-hour cutoff. The completion sentinel and
revocation journal live outside the disposable run directory. The sentinel
contains no owner or grant identifier. The mode-`0600` revocation journal is
secret-bearing and contains only the completion attestation, exact revocation
authority, endpoints, status, and server-bound cutoffs defined by the design.

## Review focus

- Malicious discovery, cross-origin redirects, ambient proxies, cookies, and
  loopback addresses outside the callback fail before resume reads. Task 2 owns
  the tests.
- A callback with wrong state, issuer, host, port, path, duplicate query values,
  or a second request fails closed and closes the listener. Task 2 owns tests.
- Browser login never fills credentials in a frame or after an origin, path, or
  `next` mismatch. Handoff data never reaches output or artifacts. Task 4 owns
  tests.
- Crash, timeout, unknown create response, replay near the cutoff, and a second
  production invocation cannot produce a second resume. Task 3 owns tests.
- Candidate changes to names, identifiers, structure, links, numbers, bounds, or
  extension data fail before create. Task 3 owns tests; the manager owns
  semantic review.
- Source IDs cannot inhabit target mutation types. No path can call
  `delete_resume`, a mutation outside create/photo/crop, or an unknown tool.
  Task 3 owns tests.
- Revocation cannot trigger SDK reauthorization. Restart after sentinel write
  permits revocation-only recovery and no resume operation. Access expiry cannot
  create a false revocation result while refresh authority remains live. Tasks 2
  and 3 own tests.
- A crash after revocation-journal sync but before sentinel write cannot reopen
  create. Recovery restores and syncs the sentinel before revocation or journal
  deletion. Task 3 owns the exact crash-point test.

## Task 1: OAuth SDK compatibility

Write failing table tests first, then make the smallest server change:

1. Prove legacy registration still accepts the current three-field request.
2. Prove the SDK loopback request accepts exact `application_type: native` and
   returns a public client with no secret.
3. Reject non-string, empty, duplicate, and non-`native` application types, and
   continue rejecting unsupported SDK metadata fields. Reject `native` when any
   redirect is empty, non-loopback, or mixed with a loopback redirect.
4. Prove authorize accepts missing or exact canonical `resource`; reject empty,
   duplicate, encoded variants, path variants, and other origins without issuing
   a code.
5. Prove authorization-code exchange accepts missing or exact canonical
   `resource`; reject every mismatch as `invalid_grant` without consuming the
   code or inserting tokens. Refresh requests reject `resource`.
6. Prove protected-resource metadata advertises exactly `resumes:read` and
   `resumes:write`, while the authorization-server metadata retains its existing
   exact scope list and the bearer challenge remains unchanged.

Run:

```bash
cd apps/server
REQUIRE_TEST_DB=1 \
  TEST_DATABASE_URL=postgres://aboutme:aboutme_dev@127.0.0.1:20432/aboutme?sslmode=disable \
  go test ./internal/oauthsrv -count=1
```

Expected: the package passes once. Do not retry a failure. The report lists
every changed line in the strict registration and form allowlists.

## Task 2: SDK transport and browser coordinator

Use the official SDK APIs directly:

- `auth.NewAuthorizationCodeHandler` with public dynamic registration and the
  exact loopback redirect;
- `mcp.StreamableClientTransport` with `DisableStandaloneSSE: true` and
  `MaxRetries: -1`; and
- `mcp.NewClient`, `Client.Connect`, `ClientSession.ListTools`,
  `ClientSession.CallTool`, and `ClientSession.Close`.

Test first and implement:

1. Strict origin parsing and one restricted `http.Client` with `Proxy: nil`, no
   cookie jar, exact-origin `RoundTripper`, and cross-origin `CheckRedirect`.
2. An ephemeral `127.0.0.1` listener that registers its exact URI, accepts one
   callback, checks all callback fields, and joins shutdown.
3. SDK DCR metadata containing only supported fields. Assert inferred
   `application_type: native`, PKCE S256, unique state, and canonical
   `resource`. Use protected-resource metadata without a challenge scope and
   prove the authorization URL requests exactly both resume scopes.
4. A one-shot OAuth wrapper that authorizes once and returns only
   `reauthorization_disabled` after success.
5. Atomic browser handoff, five-minute timeout, fixed errors, and cleanup that
   never formats sensitive values.
6. Paginated tool discovery requiring exactly 15 sorted names before any resume
   call. Disable client capabilities that the runner does not use.
7. Typed result decoding that rejects unstructured, oversized, unknown, or
   malformed tool results with fixed errors.

Use `httptest` servers and injected clocks, entropy, listeners, and transports.
Unit tests must not open a browser, use owner credentials, or contact the
network.

Run:

```bash
cd apps/server
go test ./cmd/mcp-workflow -run \
  'Test(Config|RestrictedHTTP|Callback|OAuthGate|BrowserHandoff|SDKClient|Tools)' \
  -count=1
go build ./cmd/mcp-workflow
```

## Task 3: Workflow safety and recovery

Write adversarial tests before implementation. Use `resume.ValidateForStore` for
the current typed document and add path-specific preservation checks.

1. Securely create, reopen, replace, and remove private artifacts. Reject
   symlinks, special files, wrong owners, wrong modes, extra credential entries,
   oversized files, and non-atomic replacements.
2. Select exactly one canonical English source and enforce the total-count cap.
   Write `source.json`; wait for `candidate.json` and `candidate-review.json`;
   verify both digests and `facts_preserved: true`.
3. Decode the candidate into the generated Go schema, omit server-owned photo,
   validate store and request bounds, and compare every preserved path. Permit
   changes only at translation paths named by the design.
4. Represent target writes with `targetHandle`. Make source-to-mutation
   conversion impossible. Enforce one create intent, no delete, and only target
   photo and crop mutations after create.
5. Persist the full create intent before send. Test definitive failure, unknown
   response, exact replay, reconciliation, server-time reversal, the 12-hour
   cutoff, deadline crossing, crash restart, and retained unresolved state.
6. Before any network or resume read, reject an existing completion sentinel.
   Persist it atomically only after all target checks. Test a crash after
   journal sync but before sentinel write. Revocation-only recovery must restore
   and sync a missing sentinel before any revocation action or journal deletion.
   A write or sync failure retains the journal.
7. Chain decimal revisions. On conflict, accept only an already exact target;
   otherwise stop without rebasing.
8. Decode photos. Require media type, dimensions, alpha rule, exact transparent
   PNG pixels, JPEG peak signal-to-noise ratio at least 35 dB, and crop parity.
9. Revoke with the design's narrow RFC 7009 exception. Test exact safe retry,
   lost response, restart after sentinel write, timely server `401`, access
   expiry, refresh `invalid_grant`, safe refresh rotation, retained uncertainty,
   and blocked SDK reauthorization.
10. Emit only the allowlisted evidence shape, bounded to 4 KiB, and remove
    secret state only after create and revocation reconciliation.

Run:

```bash
cd apps/server
go test ./cmd/mcp-workflow -run \
  'Test(Artifacts|Source|Candidate|Preservation|MutationCaps|CreateIntent|Recovery|Completion|Photo|Revocation|Evidence)' \
  -count=1
go test ./internal/resume ./internal/mcpapi -count=1
go build ./cmd/mcp-workflow
```

## Task 4: Browser launcher and local SDK proof

Devops changes the launcher and static checks. QA adds the Playwright helper and
proof orchestration. They work in disjoint files and do not weaken the raw
proof:

1. Devops adds `mcp-sdk` as a distinct launcher and container-entrypoint mode,
   plus the Playwright config mode, source allowlist, static tests, bounded
   stages, and exact mounts.
2. Build and run the runner on the host. Stage exactly one local synthetic
   fixture credential file inside the local run's private root. Mount that file
   read-only at the fixed container credential path and mount only the dedicated
   browser-handoff directory read-write. Production alone uses the validated
   owner credential source. Validate every target, owner, mode, and exact entry
   set before Playwright starts.
3. In local mode, use a reserved password fixture account. Create one fictional
   English source through the normal authenticated API, then sign out before SDK
   authorization. Do not retain fixture content.
4. Signal `browser-ready`, consume and unlink the request, enforce origin, path,
   frame, and `next` guards, fill two saved values once, approve consent, and
   write only the fixed result.
5. Supply fictional candidate and review artifacts through the host-private
   workflow directory. Prove SDK discovery, DCR, PKCE, consent, Streamable HTTP,
   exact tools, replay, conflict handling, optional photo, source immutability,
   unknown-create recovery, revocation, server `401`, and blocked
   reauthorization.
6. Inspect the private target without screenshot, trace, video, console
   attachment, or raw report. Clean all synthetic and private state.
7. Add one reviewed orchestration entrypoint with closed `local` and
   `production` modes. It creates the private run root, starts and joins the
   host runner and browser container, and passes only the mode and validated

8. Write a shell test with fake runner and container commands. Prove exact

## Worker brief and report contract

Before dispatch, the manager turns each ownership row into one self-contained
brief. Each brief repeats the objective, design and ADR authority, exact owned
paths, forbidden actions, definition of done, exact checks, and report format.
Workers must not edit an unowned path, perform Git operations, read owner data,
contact production, or change a design contract.

Each report lists every new, changed, and deleted file; the author's hunks in a
shared file; every check run and its result; every required check not run with
the exact command and reason; evidence paths; and open items. A report never
claims a check that did not run.

## Integrated gate and production order

After each report, the manager reads the exact diff and existing evidence. After
all author tasks:

1. Dispatch one fresh `gpt-5.6-sol` reviewer. Return findings to the owning
   author and have the same reviewer confirm fixes without local test reruns.
2. Run server builds, vet, tests, and lint through hosted candidate CI.
3. Run the synthetic browser and SDK suites on a hosted runner. Any necessary
   local interaction proof follows the bounded exception above. Keep owner
   credentials and resume content out of CI.
4. Commit only reported file sets. Push v0.4.4 alone to `main` and require green
   GitHub CI on that commit.
5. Tag v0.4.4 and wait for its immutable release images.
6. In the clean tagged release worktree, rerun `make dev-https-mcp-sdk-check`
   with the resolved release image digests. Require the private 24-hour
   attestation to bind the tagged commit and every current identity from the
   design.
7. Run the production OpenTofu plan and deploy v0.4.4 through the production
   runbook. Stop on an unexpected destroy.
8. Validate the deployed image digests against the attestation, then run
   `scripts/mcp-owner-workflow.sh production` once. The manager reads
   `source.json`, writes and separately reviews `candidate.json`, and writes the
   digest-bound review while the joined runner waits on the private handoff.
9. Require exactly one private Vietnamese target, unchanged English source, safe
   revocation and recovery, post-revocation `401`, blocked reauthorization,
   durable completion sentinel, cleaned secrets, and allowlisted evidence.

The owner may inspect or edit the private resume later. Publication and any
further production resume creation remain outside this authorization.
