# Passkey second-factor implementation plan

Status: accepted for implementation from base `e05dd7b3`. The product design,
contract sources, plan, and acceptance rows passed independent Sol review.
Frontend work remains blocked until v0.4.1 is integrated into this release base.

**Goal:** Ship v0.4.2 with optional passkey second-factor enrollment, pending
login, sensitive-action verification, deliberate removal, single-use recovery
codes, notifications, and safe rollback enforcement in Vietnamese and English.

**Architecture:** PostgreSQL owns factor, pending, recovery, ceremony, session,
and authority state. Every issuer and sensitive mutation follows the accepted
user-lock and authentication-epoch contract. A durable DynamoDB minimum-release
fence prevents the supported deploy path from starting an image that cannot
enforce an enrolled account's factors.

**Tech stack:** Go, PostgreSQL, sqlc, OpenAPI, Nuxt 4, Vue 3, TypeScript,
WebAuthn, OpenTofu, DynamoDB, ECS, Vitest, and Playwright.

**Spec:** `docs/design/second-factor-authentication.md`,
`docs/design/passkey-second-factor-contract.md`,
`docs/design/passkey-release-fence.md`,
`docs/adr/0048-passkey-second-factor-authentication.md`,
`docs/design/budgets.md`, `docs/design/security.md`, `docs/design/api.md`, and
the new `AC-AUTH-*` and `AC-SEC-*` rows.

The contract sources satisfy these prerequisites:

- The architect settles exact API wire schemas, mail event schemas, passkey JSON
  conversion rules, recovery-code download format, and the v0.4.2 boundary for
  TOTP routes and capability fields.
- The architect settles the DynamoDB table and item contract, version encoding,
  consistent-read rule, conditional update, deploy role, and deletion
  protection.
- The architect adds every numeric limit to `docs/design/budgets.md`.
- The accepted dependency decision pins `github.com/go-webauthn/webauthn`
  v0.18.2, verified as latest stable against its primary official source.

Backend, mail, and devops work may start from the clean recorded base after the
contracts pass review. Before either frontend task starts, the manager
integrates the v0.4.1 account-localization commit into the v0.4.2 base. No
worker copies files from the dirty v0.4.1 worktree. The fence-aware deploy task
starts only after the deployment alarm-suppression maintenance commit is also
integrated into the v0.4.2 base.

## Global constraints

- v0.4.2 implements passkeys and recovery codes. It does not implement TOTP
  storage, enrollment, verification, QR rendering, encryption keys, or UI.
- Existing accounts, sessions, grants, and unenrolled login behavior stay valid
  at authentication epoch `0`.
- Primary password or provider authentication never creates a session for an
  enrolled account. It creates a five-minute pending authentication.
- Pending authentication authorizes no session, account, resume, consent, MCP,
  or settings route.
- Passkey registration and assertion require the exact origin and relying-party
  ID, user presence, user verification, account binding, canonical unpadded
  base64url, and replay-safe ceremony consumption.
- Recovery codes are returned once, stored only as domain-separated SHA-256
  digests, never logged or persisted by the web app, and consumed atomically.
- Factor changes advance the authentication epoch, revoke other browser sessions
  and all connected-agent grants and token families, and rotate the deliberate
  current session under the accepted lock order.
- Password reset and provider linking preserve factor enforcement. There is no
  email, support, operator, password, or provider bypass for a lost factor.
- Every factor mutation uses a current-epoch cookie session, synchronizer CSRF,
  exact Origin, strict JSON, recent primary proof, and recent factor or recovery
  proof when enforcement already exists.
- Every security mail insert commits with its mutation. Mail, logs, metrics,
  traces, evidence, and exports contain no factor secret or stable credential
  material.
- `PASSKEY_ENROLLMENT_ENABLED` defaults to false. The flag controls registration
  options and completion. Disabled completion consumes its matching ceremony,
  stores no credential, and returns the uniform 404. Assertion, removal,
  recovery, and state reads remain available.
- The first production deploy keeps enrollment disabled. The release fence is
  raised only for a capable healthy release, before the flag is enabled.
- The resume schema, renderer, public pages, public resume JSON, PDF, and MCP
  tool schema do not change.
- Only the top manager performs Git operations, pushes, tags, deploys, or
  changes the release fence or enrollment flag.
- Every worker starts with `git status --short`, reads the named authorities,
  writes a failing test first, and stops on a contract conflict or overlapping
  ownership.
- GitHub CI runs tests, builds, lint, database, browser, and infrastructure
  checks. Workers write regression tests before implementation and report the
  checks as unrun pending hosted verification.
- Workers do not run local tests, builds, lint, installs, database writes,
  browsers, or development stacks.
- At most four workers run across all managers and worktrees. Tasks at the same
  dispatch order may overlap only when their owned paths are disjoint.
- Code, tests, comments, and living docs do not cite this plan or its task
  numbers. Write short plain text with no em dash.

## Review focus

- Race first enrollment, final-factor removal, recovery-code use, ceremony
  completion, session rotation, grant reuse, and authorization-code exchange.
  Each race must have one valid winner and no partial authority.
- Attempt password, every provider, password reset, stale cookie, stale bearer,
  silent OAuth consent reuse, old authorization code, and recovery replay paths
  around the pending and epoch boundaries.
- Reject wrong origin, relying-party hash, ceremony type, purpose, account,
  binding, epoch, user handle, verification flag, signature counter, padded
  base64url, duplicate JSON keys, unknown fields, invalid UTF-8, and oversize
  input before state changes.
- Verify every flag-off, browser-cancel, unsupported-browser, expired pending,
  exhausted-attempt, lost-factor, notification-failure, and outbox-failure path
  fails closed without exposing account or credential state.
- Verify Vietnamese and English copy, phone and desktop layout, focus, live
  announcements, one-time recovery display cleanup, and safe return paths.
- Adversarially review the DynamoDB conditional update, deploy-role boundary,
  nonexpiring operation lock, lower-version rejection, rollback, activation, and
  failed-deploy restoration before any production write.

## Integrated verification

After the author changes are integrated, the top manager commits the exact
candidate locally and obtains the fresh integrated review. The original authors
fix every finding, and the same reviewer confirms those fixes. Only then does
the manager push the candidate branch and run
`gh workflow run ci.yml --ref <branch> -f base_sha=<sha>` with the full trusted
ancestor SHA. The manager verifies that the run SHA is the unchanged reviewed
candidate and obtains these checks from GitHub CI. Do not run them locally:

```bash
make schema-check
make sqlc-check server-test-db server-test-integration server-migration-test
make server-build server-vet server-test
(cd apps/server && golangci-lint run ./...)
(cd apps/server && govulncheck ./...)
make api-check
make web-lint web-typecheck web-test web-build
make web-source-manifest-check
make web-e2e
bash -n deploy/aws/scripts/deploy.sh deploy/aws/scripts/deploy_test.sh
bash deploy/aws/scripts/deploy_test.sh
tofu fmt -check -recursive deploy/aws
```

GitHub CI also runs `tofu init -backend=false -input=false` and `tofu validate`
in `deploy/aws/bootstrap`, `deploy/aws/probe`, and `deploy/aws/prod`. The docs
job compiles and lists the passkey browser mode through `make operational-test`.
That list result is not acceptance evidence. The separate
`passkey-browser-proof` job starts the repository HTTPS harness, builds the
pinned browser image, executes `make dev-https-passkey-check` against the exact
candidate, uploads bounded secret-free evidence from fictional accounts, and
uses `if: always()` cleanup for the stack and runner-local database. It uploads
only `.dev/native-https/evidence/passkey-*`. The manager verifies that job and
artifact before the release gate. The manager does not rerun an author's checks.

## Release gate

The top manager owns the commit, push, tag, fence, flag, and deploy sequence:

1. Integrate one exact v0.4.2 file set and obtain the fresh integrated review.
2. Push the release commit alone to `main` and wait for green GitHub CI on that
   exact commit.
3. Tag `v0.4.2`, wait for release images, and run the reviewed production
   OpenTofu plan. Stop on any unexpected destroy or fence replacement.
4. Apply reviewed infrastructure changes and deploy `v0.4.2` with passkey
   enrollment disabled.
5. Run the first bounded production proof below. Prove unenrolled password and
   provider login, disabled enrollment, existing sessions, connected agents, and
   health checks.
6. Run the serialized activation operation. It acquires the durable lock, raises
   the fence conditionally to v0.4.2, and releases the exact owned lock after
   the outcome is known. Do not lower the fence on failure.
7. Enable passkey enrollment through the reviewed OpenTofu apply, then redeploy
   the same tag through a new serialized deploy operation.
8. Run the second bounded production proof below with only the dedicated
   fictional account named in the release brief under the owner's standing
   v0.4.x authorization. Prove enrollment, pending login isolation, recovery,
   epoch revocation, both locales, and final factor removal.
9. Record bounded secret-free evidence. A failure after enrollment enablement is
   fixed forward or uses an image at or above the fence.

GitHub CI cannot observe the deployed fence, enrollment flag, live identity
providers, or production origin, so steps 5 and 8 are the only production
browser exceptions. Before each run, the manager confirms at least 8 GiB of
available memory, no other aboutme local check, and no active aboutme
development stack. Use one browser profile and one command at a time:

```bash
common_dir=$(git rev-parse --path-format=absolute --git-common-dir)
flock -n "$common_dir/aboutme-local-check.lock" \
  timeout --signal=TERM 60m \
  systemd-run --user --scope --collect \
    -p MemoryMax=2G -p MemorySwapMax=0 -p CPUQuota=200% \
    /usr/bin/google-chrome \
      --user-data-dir="$PWD/.dev/v0.4.2/production-browser-profile" \
      --no-first-run --new-window https://aboutme.vn
```

The proof starts no local product stack. On success, failure, a blocker, or an
unexpected browser exit, remove only the fictional account's proof factors,
recovery plaintext, and sessions, then log out before accepting the release. If
cleanup cannot finish in the current run, use the same bounded command for a
cleanup-only session before any further release action. If the lock, hard cap,
memory floor, named account, or isolated profile is unavailable, record the
proof as blocked. Never fall back to an uncapped browser or the owner's account.
